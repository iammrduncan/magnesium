# From the mocks to a working Magnesium

**Status: plan (2026-10-13).** The owner approved the mock direction ("I really like this", D9 in [doc 09](09-decisions-and-open-questions.md)). This doc says what has to be built so each mocked screen works for real. Nothing here is built. Upstream facts come from docs 06 to 08 and 11 (read from source, not run).

**Result:** about half of what the mocks show is stock T3 Code. That includes the thread view, composer, approvals, diff panel, model switching with handoff, connections and the scheduler. The other half is ours, in seven pieces:

1. **A shell layer:** our sidebar body, the footer, and routes.
2. **A home feed:** "needs you" gathered from every source.
3. **Rooms.**
4. **A fleet view:** machines, GPUs and jobs.
5. **An app host:** registry, frame, actions and footer items.
6. **A KB bridge for Brain.**
7. **A phone path.**

Each piece is a module in `magnesium/server` plus pages in `magnesium/web` (doc 11). Each has a phase, and each mock board is that phase's acceptance test.

## The new server pieces

All in `magnesium/server`, on the second RPC route `/api/magnesium/ws` with upstream's auth (doc 11). Every machine that runs agents has a Magnesium server; the **hub** runs the gathering modules (Home feed, Fleet, App host, push) and serves the web UI (D15). Each stream follows doc 06:

- a bounded snapshot with a sequence number;
- `subscribe(afterSequence)`;
- `history(cursor)`;
- about 50 ms coalescing;
- byte-budget tests.

| Module                                    | Holds                                                           | Streams                                                                        | Calls out to                                                               |
| ----------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| **Home feed**                             | Nothing of its own; merges sources                              | `home.needs`, `home.summary`                                                   | Stock RPC (runtime requests, threads, scheduled tasks), Rooms, Run history |
| **Run history**                           | Every scheduled run and its result                              | `schedule.runs`                                                                | Thread-launch events in-process                                            |
| **Rooms**                                 | Rooms, members, message log, per-bot cursors, routing decisions | `rooms.list`, `rooms.log`                                                      | Thread management (seats), the decision model                              |
| **Fleet**                                 | Machine and GPU samples from each Magnesium server (D21)        | `fleet.machines`, `fleet.jobs`                                                 | Each server's metrics collector; the dBrain API                            |
| **App host** (hub; machine parts per D55) | App registry, pins, versions, data scopes, footer declarations  | `apps.list`, `footer.items`                                                    | App tools through approvals; the extension model in doc 14                 |

## Security for apps and the footer

- **App actions ask first.** A tool marked "asks first" in an app's manifest goes through an approval, and that approval shows on Home and on the phone like any other.
- **Each app has a data scope.** It reads only what its manifest names. KB content stays local and never goes to a hosted model.
- **Apps and footer items follow the model in [doc 14](14-apps-and-footer-extension-model.md)** (D24): a manifest per app, Hermes Desktop's registry and footer item, DeepSeek Harness's fail-closed approvals, and app UI in sandboxed frames that talk to the hub only through proxied tool calls.
- **Apps built by agents are versioned and attributed** to the profile and thread that made them. Turning one off stops its tools and its footer item.
- **The sandbox rules apply** to whatever an app runs on a machine (dBrain's `AGENTS.md`, doc 11).
- **Push carries no content.** A web push holds a count and a link ("1 needs you"). Details load in the app over the authenticated socket, because push goes through outside services (D16).
- **One front door for the PWA, for one person** (D14). HTTPS on your network (a tailnet, a LAN or a reverse proxy), device pairing instead of the removed hosted sign-in (D13), tokens kept on the server. A PWA needs HTTPS for its service worker and push anyway.
